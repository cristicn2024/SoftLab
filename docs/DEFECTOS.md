## Orden recomendado de corrección

1. **Primero DEF-01, DEF-08 y DEF-09**: autenticación/roles, política CORS y configuración segura de la base. Resolverlos como grupo de seguridad y validar los entornos demo y producción.
2. **Luego DEF-02**: sanitización/autoescape del PDF y aislamiento del renderer. Tiene dependencia funcional de la autorización correcta de escritura de plantillas.
3. **Después DEF-03 y DEF-04**: validar catálogo/precios y referencias tenant-scoped dentro de `OrdenesModule`; cubrir también cobro/corte de caja.
4. **En el dominio clínico, DEF-05 antes de DEF-06**: definir la expansión de perfiles a estudios y su persistencia; después hacer que el PDF se construya desde resultados por parámetro.
5. **En mantenimiento, DEF-07 y DEF-12**: confirmar reachability de los avisos, actualizar dependencias corregidas de runtime y después los árboles de herramientas frontend; correr suites/build tras cada grupo.
6. **Después DEF-10, DEF-11, DEF-13 y DEF-14**: completar catálogo de médicos, paginar worklist, dejar lint limpio y sanitizar errores públicos.

## Defectos que dependen entre sí

- **DEF-01 → DEF-08**: la exposición por CORS agrava el abuso desde sitios web porque no hay sesión verificable y los encabezados son falsificables.
- **DEF-01 → DEF-02**: el endpoint de plantillas carece de autorización efectiva; restringir quién publica plantillas reduce quién puede introducir texto que llega al renderer. Aun así, hay que escapar datos de pacientes/resultados por separado.
- **DEF-03 → DEF-04**: al resolver conceptos por tenant y precio del servidor, debe hacerse en la misma validación que confirma que paciente, sucursal y médico pertenecen a ese tenant.
- **DEF-05 → DEF-06**: el PDF no puede emitir correctamente resultados de perfiles hasta definir cómo se expanden y guardan sus estudios/parámetros.
- **DEF-07 / DEF-12 → gates de CI**: actualizar versiones puede modificar reglas/herramientas y cambiar el resultado de DEF-13; ejecutar lint, type-check, tests y build después de las actualizaciones.

## Preguntas abiertas para el equipo

1. ¿La API es exclusivamente para demo con datos ficticios o ya atiende/atenderá datos reales? ¿Existe un gateway externo que autentique y reescriba `x-user-*` y `x-tenant-id`? No está en el repositorio inspeccionado.
2. ¿Los precios de la orden deben ser inmutables al crearla o se permite precio manual/descuento desde recepción? El código actual permite que el cliente establezca los dos importes.
3. ¿Un perfil debe crear una fila de resultado para cada estudio asociado, o la captura se implementará en otro módulo? El esquema relaciona perfiles y estudios, pero el repositorio de worklist no los expande.
4. ¿Cuál es el formato clínico aprobado del PDF para estudios con varios parámetros y unidades? El mapper actual toma solo el primer resultado y usa `mg/dL` fijo.
5. ¿El `GET /doctors` se retiró intencionalmente o falta implementarlo? La pantalla oculta su error.
6. ¿Qué orígenes y credenciales deben usarse en desarrollo, demo y producción? Actualmente CORS queda en `*` si no se configura y Compose trae una contraseña de conveniencia.
7. ¿Qué compromisos de tiempo/tamaño se esperan para la lista de trabajo? No hay límite ni paginación en la consulta observada.
